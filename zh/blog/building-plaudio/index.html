建造 Plaudio

開源

今天我發佈了一個小東西，叫做 Plaudio。它是為 Plaud Note 錄音機系列設計的「聲紋庫優先」說話人標記工具，以 Python 撰寫，AGPL-3.0 授權，僅支援 macOS Apple Silicon。今早 v0.1.0 已上架 PyPI。

這是個極為私人的專案：我是為了自己實際參與的會議形狀而建造它的。我用的錄音機是 Plaud Note Pro。我需要的逐字稿品質高到「誰說了什麼」與「說了什麼」同樣重要。我參與的會議通常有四到七個人，其中許多是同事，而他們的聲音對一個從未見過他們的說話人分離模型來說，聽起來很相似。

最後這一點，是現有工具讓我失望的地方。

群集合併的問題

主流的本地說話人分離流程（pyannote-audio 3.1 預設模式）會把說話人分群，再為每個群組貼上標籤。當聲音差異足夠大時，這個方法很好用。但當會議裡有四個人共享相似的音高、口音與會議語域時，pyannote 經常會把他們塌縮成一個 SPEAKER 群集。模型很有信心。輸出充滿信心地錯了。每一段話都被歸給這四人中的一個。其餘三人從逐字稿中消失。

我在五月底的一場會議遇到了這個確切的失敗模式。四位資深同事、相似的語域、節奏快速的對話。分離後的逐字稿裡，其中三人完全消失了，他們的所有內容都被歸到第四人身上。第一眼看起來逐字稿是正確的。直到我憑藉自己當時的記憶回讀，才發現標籤在欺騙我。

一份充滿信心的錯誤逐字稿比沒有逐字稿更糟。它是你可能引用、轉述、分享的東西。

你可能會把某個決定歸給一個並未做出該決定的人。隱私的故事還行，但失敗的故事不行。

解法

Plaudio 採取了不一樣的進路。它不去分群再把群配對到 profile，而是逐窗匹配。

你為每位常出現的說話人做一次「登錄」（enrolment）：用一段乾淨的 30 秒音檔，並徵得對方同意。登錄時 pyannote 的分離流程會產出一個 256 維的嵌入向量。Plaudio 將其存在一個本地的 JSON 檔案中，權限 0600。

對於每一場新會議，Plaudio 會用 2 秒視窗、1 秒位移在音訊上滑動。每個視窗都由 pyannote 嵌入，然後獨立地與所有已登錄的 profile 進行餘弦相似度匹配。視窗自己選擇匹配對象。連續同標籤的視窗合併成段。這些段套疊到原本的逐字稿區段之上。

相似的聲音不再被塌縮成一個群集，因為根本沒有分群這一步。每個視窗都是自己的決定。未匹配的視窗保留為 Unknown，這正是還未被登錄的人的正確答案。

實作很小（幾百行 Python），但實際效果很大。同樣四人同事的會議，現在能正確標記，因為這四人早已在我的聲紋庫裡。

v0.1 ships 什麼

整個「音訊進」的半邊管線：

plaudio transcribe meeting.mp3
plaudio match meeting.mp3 meeting.plaud.json --threshold 0.55
plaudio enrol clean-30s-clip.mp3 --name "Alice Smith" --start 0 --end 30
plaudio db ingest meeting.plaud.json --meeting-id 2026-05-30-team
plaudio db search "deadline" --speaker "Alice Smith"

加上聲紋庫管理工具、互動式標記 CLI，以及一個 doctor 指令會告訴你缺少哪一個相依套件。

技術棧是 mlx-whisper 負責 ASR（運行在 Neural Engine 與 GPU 上，M 系列晶片約六倍即時速度）、pyannote-audio 3.1 提供嵌入模型，以及 SQLite 配上 FTS5 trigram 分詞器作為可搜尋語料庫。trigram 分詞器是讓中英文混合搜尋能順利運作的關鍵，這對我參與的會議來說很重要。

Plaud 雲端同步會在 v0.2 加入。完整的 README 與 技術棧理由 都在 GitHub 上。

我從建造這個過程中正在學到的

三個觀察。

第一，為自己而建是一種紀律，不是退路。我從一開始就有清晰的測試案例（我自己的會議）。我知道成功是什麼樣子（正確的名字出現在逐字稿裡）。我是第一個使用者、第一個 bug 回報者，也是第一個受益者。發佈開源時的誘惑是把範圍太早擴大。紀律是先把窄的事情做好，再讓其他人的興趣決定要不要擴大。

第二，審計關卡比程式碼更重要。我有一份從工作 vault 自動生成的私人詞表：同事姓氏、計劃代號、內部縮寫。每一次 commit、每一次 CI build 都會掃描差異對照這份詞表。pre-commit hook 是強制的；--no-verify 旁路是被個人規則禁止的。在我寫任何 Plaudio 程式碼之前，我先建好了這套審計基礎設施，因為一旦程式碼進入公開倉庫，它就永遠被發佈了。洩漏比缺失功能更難回復。

第三，垂直切片比水平層級更快出貨。Plaudio 每一個子指令都是端到端建造完才開始下一個：測試、實作、CLI 都在同一個切片裡。函式庫抽取時的誘惑是先建好所有核心演算法，再去包所有的 CLI。紀律是先把單一指令端到端做出來，再做下一個。

接下來

v0.1 已經上線。v0.1.1 有一份小型的已知後續修正清單：一個預設旗標錯了、一條錯誤路徑回傳原始例外而非友善訊息、兩個棄用警告需要清理。v0.2 加入 Plaud 雲端同步。

如果你有一台 Apple Silicon Mac 上的 Plaud Note Pro，且遇到同樣的群集合併問題，請用 pip install plaudio 安裝。如果沒有，這個工具大概不適合你，這是設計使然。
